## 3. 运行入口与付费边界

在 `langchain/` 执行；环境准备见 [Day 1](day01.md)。

```bash
npm run example:tool
npm run example:structured
```

这两个默认入口不需要 API key。
如果你自主选择 live 模式，可分别使用下面的入口；它们可能产生供应商费用。

```bash
npm run example:tool -- --live
npm run example:structured -- --live
```

真实后端是否支持工具选择、原生结构化输出等能力，需要按供应商与具体模型验证。
今天的离线通过不替代这些兼容性检查；未执行 live 时明确记录“未验证”。

## 4. 概念速查：从声明到执行

| 阶段 | 输入 → 输出 | 你必须检查什么 |
|---|---|---|
| 工具声明 | 名称、描述、Zod schema → 工具定义 | 描述能力不等于授权执行 |
| 模型请求工具 | 消息 → 带 `tool_calls` 的消息 | 名称、参数、调用 id |
| 应用执行 | 白名单 + 合法参数 → 函数结果 | 权限、运行时验证、业务限制 |
| 回传结果 | 函数结果 → `ToolMessage` | `tool_call_id` 与原调用一致 |
| `withStructuredOutput` | 消息 → schema 对象 | 下游收到对象，而非“看起来像 JSON”的文字 |
| Zod 校验 | 未知值 → 合法对象 / 错误 | TypeScript 类型不能代替运行时验证 |

`bindTools` 只让模型知道工具 schema，不会替应用执行函数。
本课程订单工具返回 JSON **字符串**；检查业务字段前先理解其序列化边界。
工具可被调用不代表它可以访问任意订单；生产权限仍由可信业务服务检查。

## 6. 三个分级练习

### A · 基础：把三类输入分开

- **输入**：`{"orderId":"demo-001"}`、`{"orderId":"demo-999"}`、`{"orderId":"demo-1"}`。
- **操作**：先做 `OrderInputSchema` 校验，再理解工具函数的执行结果。
- **预期行为**：第一项命中 fixture；第二项合法但查无数据；第三项在参数边界被拒绝。
- **加测**：传入 `{"orderId":"demo-001","admin":true}`，严格 schema 不接受额外字段。
- **证据**：记录“校验结果 / 是否执行 / 业务结果”，不要只写成功或失败。

### B · 进阶：追踪一次手动工具循环

- **输入**：一个名为 `lookup_order`、参数为 `demo-001`、带匿名调用 id 的工具请求。
- **操作**：从 `AIMessage.tool_calls` 跟到白名单、参数校验、函数调用，再跟到 `ToolMessage`。
- **预期行为**：结果消息保留对应的 `tool_call_id`，模型才有可对应的工具执行结果。
- **反例**：工具名改成 `delete_order` 时，手动执行器回传 `UNKNOWN_TOOL`，不执行任何删除。
- **反例**：合法工具配非法参数时回传 `BAD_ARGS`；缺调用 id 则不能构造合法的配对结果。
- **限制**：不要给练习添加任意 shell、文件读取或真实订单修改工具。

### C · 挑战：验证工单对象，而不是信任 JSON 外观

- **输入**：`{"category":"order","summary":"查询匿名订单配送状态","requiresHuman":false}`。
- **操作**：按 `TicketSchema` 验证，再分别改成未知分类、空摘要、字符串 `"false"`。
- **预期行为**：合法对象通过；`category` 只接受 `order/refund/other`，摘要长度为 1–200，转人工字段必须是 boolean。
- **加测**：超过 200 字的摘要与额外字段都应被拒绝；保留脱敏后的错误类别。
- **思考**：即使对象通过，也不能据此断言订单状态真实、退款符合政策或已完成鉴权。

## 7. 证据清单与易踩坑

- [ ] 我能分别展示非法参数、合法但不存在、合法且存在的行为。
- [ ] 我记录了请求 id 与 `ToolMessage.tool_call_id` 的对应关系。
- [ ] 我确认未知工具不执行，非法参数不进入正常业务调用。
- [ ] 我记录了一条合法工单与至少两类非法工单。
- [ ] 我没有把 schema 校验说成授权、业务审批或事实验证。

TypeScript 的 `as Ticket` 不会在运行时验证模型输出。
直接工具调用的校验异常，与手动执行器包装后的 `BAD_ARGS` 消息不是同一种接口结果。
不要把工具结果的 JSON 字符串直接当对象读字段，也不要丢掉结果对应的调用 id。
供应商兼容接口不保证所有结构化策略可用；工具强制选择与 native schema 能力分别检查。

## 8. 五道自测（附简答）

1. **`bindTools` 会执行工具吗？** 不会；应用或 Agent 执行循环负责调用函数并回传结果。
2. **`demo-999` 是非法参数吗？** 不是；格式合法，业务结果表示不存在。
3. **为什么工具结果需要调用 id？** 它把结果与原始请求配对，尤其在多工具调用时不可省略。
4. **对象通过 Zod 就能自动退款吗？** 不能；授权、政策、幂等和审批是独立业务检查。
5. **所有 ChatOpenAI 兼容后端都支持同样的结构化能力吗？** 不保证，要对具体模型与后端验证。
