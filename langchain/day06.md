# Day 6：把本地 RAG 拆成可追踪的证据链

> 今天你要从回答中的来源一路追到 Markdown 和切片，并解释资料不足时该如何停止推断。

**对应正文**：[10 · RAG](lessons/10-rag.md)。
**前置**：[Day 3](day03.md) 的运行时验证、[Day 5](day05.md) 的状态与数据生命周期。
**默认模式**：匿名 Markdown、词项计数向量、内存向量库和固定假回复；没有真实语义 Embedding。

## 1. 今日目标

- [ ] 你能分开说明建立索引与处理问题这两条链路。
- [ ] 你能从检索结果找到原文件、切片内容与来源元数据。
- [ ] 你能用词表之外的问题暴露离线检索的能力边界。
- [ ] 你能区别检索有证据、答案引用合法、答案事实正确三种检查。

## 2. 限时学习顺序（约 150 分钟）

| 时间 | 你做什么 | 你留下什么 |
|---|---|---|
| 0–25 分钟 | 阅读 10，区分索引和问答 | 两条输入输出链路 |
| 25–50 分钟 | 阅读三篇 fixture 与 rag helper | 来源、分块与向量定义 |
| 50–70 分钟 | 默认运行，检查命中内容 | 问题 → 切片 → 原文件对应 |
| 70–125 分钟 | 做三组检索与分块练习 | 命中、拒答依据、词表漏检反例 |
| 125–150 分钟 | 自测、复盘与 Review | 一份不夸大离线能力的验收说明 |

今天先验证证据流，不从采购向量数据库或微调模型开始。

## 3. 默认入口与可选真实向量

在 `langchain/` 执行；没有 key 也可以完成必做练习。

```bash
npm run example:rag
```

源码中的离线向量是四维词项计数，不是训练得到的语义表示。
默认回复也写在假模型脚本中，不是模型根据检索资料推理生成的答案。
如果你自主选择真实供应商，才使用下面的入口。

```bash
npm run example:rag -- --live
```

live 需要 `.env` 中的 `OPENAI_API_KEY`、`OPENAI_MODEL` 与独立的 `OPENAI_EMBEDDING_MODEL`。
这条路径会把文档 / 问题送去生成 Embedding，并进行聊天生成，可能产生两类费用。
只用匿名 fixture；真实检索采用 top-k 演示，不沿用词项模拟的 `0.1` 阈值。
未执行 live 时不要填写召回率、模型费用或供应商兼容性结论；默认也不自动追踪。

## 4. 概念速查：逐站说明输入与输出

| 站点 | 输入 → 输出 | 你关注的契约 |
|---|---|---|
| 读取资料 | Markdown → `Document[]` | `pageContent` 与相对 `metadata.source` |
| 切片 | Document → 多个小 Document | 内容长度、重叠、来源保留 |
| 文档向量化 | 字符串数组 → 数值向量数组 | `embedDocuments`，一段文本对应一个向量 |
| 问题向量化 | 问题字符串 → 一个数值向量 | `embedQuery`，与文档向量维度一致 |
| 检索 | 问题 / 向量 → 带来源的切片 | 相似度不是事实可信度 |
| 组装上下文 | 检索切片 → 资料文本 | 文档是数据，不是高权限指令 |
| 生成与验收 | 问题 + 资料 → 回答 / 检查结果 | 空证据、引用、事实分别检查 |

索引链路是 `文件 → Document → 切片 → embedDocuments → 向量库`。
问答链路是 `问题 → embedQuery → 检索 → 带来源的上下文 → 模型 → 验收`。
改动资料后不会凭空刷新旧索引；重建、增量更新与版本管理需要应用明确安排。

## 6. 三个分级练习

### A · 基础：把一次命中追到原文

- **输入**：“收到商品后几天内可以申请退货？”
- **操作**：从 `retrieveEvidence` 的结果记录来源与 `chunkId`，再读对应的 Markdown 段落。
- **预期行为**：你找到 `fixtures/knowledge/returns.md` 中的退货依据，同时看到包装和使用条件。
- **证据**：记录实际切片内容、来源和上下文，不只保存假模型那句固定“7 天”回答。
- **检查**：若你只留下时间而删掉条件，说明这会怎样误导使用者。

### B · 进阶：用两个反例识别能力边界

- **输入一**：“明天的天气是什么？”；**输入二**：“不想留着这个商品了，多久能寄回去？”
- **操作**：保持离线词表和阈值不变，分别检查检索切片与 `buildContext` 的结果。
- **预期行为**：这两个问题没有词表中的相关词项，离线过滤后无证据；第二个其实可能与退货语义有关。
- **结论**：第一个是资料范围外，第二个暴露手工词表漏检；不要把两者都说成知识库没有政策。
- **回答边界**：无证据应转为“资料不足”的业务分支；假模型仍给固定答案不算通过拒答验证。

### C · 挑战：改变分块，比较证据而不是只比答案

- **输入**：使用同一退货问题，在练习副本把分块设置改为 `chunkSize: 160`、`chunkOverlap: 20`。
- **操作**：重新建库，比较实际切片数量、边界、来源、检索命中内容与条件是否完整。
- **预期行为**：分块变化可以改变检索粒度，但来源路径仍保留；数量与排名以实际输出为准。
- **反例**：很短的命中只带“7 天”，条件落在别的块中；说明你为何要检查完整上下文。
- **加分项**：把带“忽略指令”文字的匿名资料视为不可信数据，不新增工具或根据资料执行操作。

## 7. 证据清单与易踩坑

- [ ] 我留下了索引链路与问答链路各自的输入输出。
- [ ] 我能从来源和切片定位到真实 fixture 段落。
- [ ] 我记录了命中、范围外、词表漏检三类问题。
- [ ] 我区分检索为空和生成拒答，没有让固定回复替我证明后者。
- [ ] 我写明真实 Embedding、召回质量和线上费用尚未验证。

词项向量只统计有限词组，不具备通用同义理解；“有 cosine similarity”不代表语义检索。
`0.1` 是离线词项模拟的测试阈值，不能复制成真实向量的生产标准。
top-k 常会返回最接近但不相关的资料，所以“返回了两个块”不代表确有证据。
引用路径存在也不够：它应来自本次检索，且回答的具体断言应由引用内容支持。

## 8. 五道自测（附简答）

1. **索引和问答为什么分开？** 资料转换可预先完成，问题到来时主要做检索与生成。
2. **`embedDocuments` 与 `embedQuery` 有什么区别？** 前者处理多段文本，后者处理一个查询，输出维度要匹配。
3. **默认向量算语义 Embedding 吗？** 不算；它是手工词项计数，用于离线验证数据流。
4. **空检索时固定回复仍说“7 天”能通过吗？** 不能；那是脚本输出，不是证据支持的回答。
5. **真实 Embedding 可直接用 `0.1` 吗？** 不应直接沿用；阈值与召回策略需要真实评估集校准。
