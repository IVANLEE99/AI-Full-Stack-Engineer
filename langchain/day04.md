# Day 4：让 Agent 管循环，让中间件守边界

> 今天你要从“我手动调用一次工具”走到“框架编排循环，但应用仍控制权限、预算与终止”。

**对应正文**：[07 · Agent](lessons/07-agents.md)、[08 · 中间件](lessons/08-middleware.md)。
**前置**：[Day 3](day03.md) 的工具白名单、参数校验和结果关联；命令均在 `langchain/` 执行。
**默认模式**：官方脚本化假模型与匿名只读订单工具；不调用供应商，不自动追踪。

## 1. 今日目标

- [ ] 你能在 Agent 历史中找出用户消息、工具请求、工具结果与结束消息。
- [ ] 你能解释 `createAgent` 接管了哪些循环步骤，哪些安全责任仍在业务侧。
- [ ] 你能区分 `beforeModel` 与 `wrapModelCall` 的位置和职责。
- [ ] 你能用调用上限、超时与明确错误出口避免无界执行。

## 2. 限时学习顺序（约 130 分钟）

| 时间 | 你做什么 | 交付检查点 |
|---|---|---|
| 0–25 分钟 | 阅读 07，对照昨天的手动循环 | 自动编排 / 应用责任对照表 |
| 25–50 分钟 | 阅读 08，定位生命周期与包装钩子 | 钩子位置说明 |
| 50–65 分钟 | 运行两个离线入口 | 消息历史与安全统计 |
| 65–110 分钟 | 完成三个分级练习 | 正常循环与预算触发证据 |
| 110–130 分钟 | 自测、复盘与 AI Review | Agent 终止条件清单 |

不要把能自动调工具理解为可以自主获得更多权限。自动化越强，应用边界越要显式。

## 3. 今天的入口

```bash
npm run example:agent
npm run example:middleware
```

预期 Agent 示例编排脚本化工具请求，中间件示例展示钩子与调用限制。
默认输出只能证明控制流接线，不证明真实模型会正确判断是否需要查询订单。
可选 `--live` 由你主动选择，可能计费；真实供应商能力与异常处理不在本页已验证范围内。
LangSmith 追踪仍需额外显式选择 `--live --trace`，不能因环境里已有 key 就自动打开。

## 4. 概念速查

| 概念 | 它做什么 | 不要误认为 |
|---|---|---|
| `createAgent` | 编排模型、工具与状态循环 | 一个自动获得业务权限的账号 |
| `systemPrompt` | 提供系统级行为指令 | 可替代鉴权或确定性校验 |
| `beforeModel` | 在模型阶段前查看 / 更新状态 | Express 的 `req, res, next` 接口 |
| `wrapModelCall` | 围绕一次模型请求调用 handler | 必须额外再调用一次模型 |
| 模型调用限制 | 约束 run / thread 的模型调用次数 | 精确的 token 或费用上限 |
| 工具调用限制 | 拦截超过额度的工具请求 | 所有配置下都会结束整个 Agent |
| 超时与图步数限制 | 限制等待时间与循环步数 | 身份授权或事实校验 |

一次用户输入可能产生多次模型调用：提出工具请求后，还要消费工具结果。
JS 参数用 `systemPrompt`、`responseFormat`，Agent 结构化结果读 `structuredResponse`。
限制工具次数、限制模型次数、限制等待时间是三个不同维度，不能只设其中一个。

## 6. 三个分级练习

### A · 基础：还原 Agent 替你做的工作

- **输入**：“查询 demo-001 的配送状态。”，使用现有匿名只读 fixture。
- **操作**：运行离线 Agent，记录消息类型与调用 ID，不只记录最后一句话。
- **预期行为**：脚本提出 `lookup_order` 请求，框架执行工具并回填对应结果，然后得到固定结束回复。
- **对照**：列出昨天你手动做的白名单、校验、执行和回填步骤，指出今天由谁负责。
- **证据**：写出执行顺序及工具结果中的 `found`；不要把固定结束文本当作事实核验。

### B · 进阶：让钩子观察过程，但不泄露内容

- **输入**：同一条匿名订单问题，保留示例原有模型与工具。
- **操作**：在练习副本中记录钩子名称、消息数量与工具名称，观察一次完整循环。
- **预期行为**：你能区分模型前的状态钩子与围绕请求的包装钩子，原有工具流程仍可完成。
- **检查**：定位 handler 的调用次数，确认日志行为不会额外发出模型请求。
- **证据**：保留顺序与统计摘要，不打印原始对话、工具参数或完整异常请求体。
- **加分项**：说明状态更新与仅修改本次模型请求为什么不是同一件事。

### C · 挑战：让预算真的触发一次

- **输入一**：保持“请求工具 → 消费结果”的脚本，把模型限制设为 `runLimit: 1`、`exitBehavior: "error"`。
- **预期一**：第二次模型阶段被限制；你不能把“查完工具但没有最终回答”当成完整成功。
- **输入二**：在独立练习中让脚本连续请求两次 `lookup_order`，工具限制为每轮一次并选择错误退出。
- **预期二**：第二次受限工具不得执行；同时保留模型上限，防止另一种错误处理策略继续空转。
- **证据**：分别记录限制类别、被阻止的动作与退出状态，不只截取一个报错字符串。
- **限制**：不注册写订单、任意 shell 或任意文件工具来“测试自主性”。

## 7. 证据清单与易踩坑

- [ ] 我能复述完整工具循环，而不只描述最终回复。
- [ ] 我明确区分框架编排与业务权限校验。
- [ ] 我记录了两个钩子的职责，并确认没有重复调用 handler。
- [ ] 我分别触发过模型与工具预算的失败条件，或明确标为尚未执行。
- [ ] 我的日志只包含匿名统计与安全错误摘要。

工具限制的 `exitBehavior: "continue"` 会用错误结果阻止受限工具，不一定结束模型循环。
模型限制和工具限制的退出策略不完全相同；按当前 JS 类型与正文配置，不猜通用默认值。
图的 `recursionLimit` 约束图执行步数，不是“最多调用模型多少次”的同义词。
Agent 的 `streamEvents()` 与 LangGraph 的 `stream(..., { streamMode })` 不是同一套消费接口。

## 8. 五道自测（附简答）

1. **Agent 会替你完成用户鉴权吗？** 不会；资源权限仍由应用与工具实现控制。
2. **一轮输入只调用一次模型吗？** 不一定；工具请求与结果消费通常需要不同模型阶段。
3. **`beforeModel` 与包装钩子的差别是什么？** 前者面向阶段前状态，后者围绕本次模型请求与 handler。
4. **限制工具后模型一定停止吗？** 不一定；取决于退出策略，因此还需模型预算与终止条件。
5. **调用次数上限等于费用上限吗？** 不等于；真实费用还取决于模型、上下文、输出和重试。
