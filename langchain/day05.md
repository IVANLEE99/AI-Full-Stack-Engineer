# Day 5：把上下文、会话状态与长期记忆分开

> 今天你要证明数据究竟存在哪里、何时进入模型，而不是凭一句“它记住了”判断记忆有效。

**对应正文**：[09 · 上下文与记忆](lessons/09-context-memory.md)。

**默认模式**：官方假模型、进程内 checkpointer 与 store，无数据库、无模型 API、无追踪。

## 3. 今天的入口与前置规则

```bash
npm run example:memory
```

示例使用 `MemorySaver` 与 `InMemoryStore`；它们都保存在当前进程的内存中。
预期你能看到同一线程的历史与按 namespace 存取的数据；实际输出由你记录。
重新运行 npm 命令会创建新进程，不能用两次独立执行证明内存跨进程共享。
本页不声明数据库、真实模型或追踪已经完成联调；今天不配置 `DATABASE_URL`。

## 4. 概念速查：三件容易混在一起的事

| 概念 | 数据在哪里 | 谁决定进入模型 | 生命周期 |
|---|---|---|---|
| 模型上下文 | 本次请求中的消息 / 文档 / 指令 | 应用构造请求 | 一次请求 |
| 短期会话状态 | checkpointer 的线程状态 | Agent / 图恢复后构造请求 | 当前线程，受存储实现限制 |
| 长期业务记忆 | store 的 namespace 与 key | 应用、工具或中间件显式读取 | 业务定义，受存储实现限制 |

“长期”描述用途，不代表 `InMemoryStore` 自动获得永久保存能力。
把值放进 store 不会让模型自动知道它；你还要定义检索、授权和注入路径。
保留全量历史也不代表全量历史必须送给模型；token 窗口、摘要与裁剪是另一个设计问题。

| 标识 | 今天的例子 | 你不能假设什么 |
|---|---|---|
| `configurable.thread_id` | `demo-thread-a` | 有线程 ID 就完成了鉴权 |
| namespace | `["users", "demo-user-a"]` | 仅使用数组路径就天然阻止跨用户访问 |
| store key | `preferences` | 同名 key 在所有 namespace 中共享 |
| 用户身份 | 匿名练习身份 | 可以由模型或客户端随意决定真实资源归属 |

这里的 `thread_id` 仍是带下划线的配置键；不要为了 JS 风格改成 `threadId`。

## 6. 三个分级练习

### A · 基础：用状态证据验证同线程两轮

- **输入一**：“练习偏好：请简短回答。”；**输入二**：“复述当前会话的历史。”。
- **操作**：在同一进程、同一个 Agent 与 `MemorySaver` 中，使用 `demo-thread-a` 连续调用两轮。
- **预期行为**：第二轮线程状态包含第一轮匿名用户消息以及已保存的消息历史。
- **验证方法**：检查返回状态或 checkpoint；固定假回复即使没有复述偏好，也不否定状态保存。
- **反例**：把第二轮换成 `demo-thread-b`，其历史不应自动继承线程 a 的消息。
- **证据**：记录线程标识、轮次与消息内容的脱敏摘要，而不是编造“模型记住偏好”的结论。

### B · 进阶：证明线程隔离与用户隔离不是一回事

- **输入**：namespace `["users", "demo-user-a"]` 的 `preferences` 写入 `{ style: "brief" }`。
- **操作**：显式读取同 namespace 的同 key，再读取 `["users", "demo-user-b"]` 的同 key。
- **预期行为**：用户 a 可读到自己的练习值，用户 b 的 namespace 中没有这条记录。
- **对照**：同一用户另开一个 thread，如果应用仍读取用户 a 的 namespace，可复用同一偏好。
- **证据**：提供“身份 / thread / namespace / key / 读取结果”表，明确哪个字段控制哪种隔离。
- **安全说明**：真实系统必须由服务端绑定身份与资源，不能信任客户端随意传入的 namespace。

### C · 挑战：拆掉“内存等于持久化”的误解

- **输入**：先在练习进程写入一条匿名状态与一条偏好，然后结束进程并重新启动。
- **操作**：在新进程使用相同标识检查旧数据；不要增加文件或数据库保存逻辑。
- **预期行为**：新建的内存实现没有上一进程的数据；标识相同不意味着数据还能恢复。
- **扩展任务**：写出换成持久化存储前必须补的迁移、连接池、权限、保留期和删除策略。
- **证据**：把“当前内存行为”与“未来数据库方案”分开记录，不把方案当成已跑通的结果。
- **限制**：今天不安装数据库依赖、不连接外部数据库，也不承诺多进程或灾难恢复。

## 7. 证据清单与易踩坑

- [ ] 我观察的是 checkpoint / store 数据，而不是假模型回复是否像“记住了”。
- [ ] 我在同一进程里比较了同线程与不同线程。
- [ ] 我分别验证或标注了 thread 与 namespace 的隔离行为。
- [ ] 我说明了 store 值进入模型的显式读取路径。
- [ ] 我把重启失效、权限校验和删除策略写进了限制清单。

只裁剪模型输入不等于删除已保存 checkpoint；数据治理要分别处理。
摘要可能改变或遗漏事实，不能作为无损存档或权限判断依据。
同一个线程被不同用户共享会带来泄露风险；随机线程 ID 也不能替代资源授权。

### 可选持久化阅读，不是今天的实施任务

数据库 checkpoint 与 store 是两个组件，不是替换一个对象就完成生产方案。
JS 的 `PostgresSaver` 从 `@langchain/langgraph-checkpoint-postgres` 导入。
`PostgresStore` 的导入路径是 `@langchain/langgraph-checkpoint-postgres/store`。
它们不属于今天默认依赖与已验证环境；参照正文与官方文档另做选型、迁移和联调。

## 8. 五道自测（附简答）

1. **store 中存在偏好，模型就会知道吗？** 不会；应用还要读取并把它加入模型可见上下文。
2. **`MemorySaver` 能跨进程重启恢复吗？** 不能；本课使用的是进程内存实现。
3. **thread 与 namespace 是同一个维度吗？** 不是；前者组织会话状态，后者组织业务记忆。
4. **换线程能证明用户鉴权完成吗？** 不能；身份与资源授权必须由应用实现。
5. **只看假模型答案能验证记忆吗？** 不能；应检查状态、读写结果和实际注入路径。
