# Day 2：把提示词当作可检查的数据管道

> 今天你要在模型调用前看清最终消息，并知道追踪会把哪些数据送到哪里。

**对应正文**：[03 · LangSmith](lessons/03-langsmith.md)、[04 · 消息与提示词](lessons/04-messages-prompts.md)。
**前置**：[Day 1](day01.md) 的离线模型与消息类型；你已经能运行 npm 示例脚本。
**默认模式**：不调用供应商、不上传追踪；假模型响应不用于判断提示词是否“更聪明”。

## 1. 今日目标

- [ ] 你能把模板变量、历史消息和当前问题分开管理。
- [ ] 你能在调用模型前检查渲染后的消息角色、顺序与内容。
- [ ] 你能解释 `.pipe()` 前后每一步的输入与输出契约。
- [ ] 你能说明 LangSmith 的用途、显式开关与数据泄露风险。

## 3. 默认运行与可选追踪

在 `langchain/` 执行；若未安装依赖，先完成 [Day 1 的准备](day01.md)。

```bash
npm run example:trace
npm run example:prompt
```

`example:trace` 这个名称不代表默认上传数据。
本课程 runtime 默认关闭追踪；即使你以前配置过 LangSmith，也必须显式选择本次行为。
没有 `--live` 时，`--trace` 不应让离线示例偷偷变成联网示例。

下面仅是你**自主选择**真实调用与追踪时的入口，不是今天的必做任务。

```bash
npm run example:trace -- --live --trace
```

使用前，你需要在自己未提交的 `.env` 配置模型供应商与 LangSmith。
这会产生供应商调用、可能的计费和外部追踪数据；只使用匿名练习输入。
没有实际执行时，记录“未执行”，不要填写假的 trace 链接、延迟或 token 数。

## 4. 概念速查：每一步只做一件事

| 组件 | 输入 → 输出 | 你检查什么 |
|---|---|---|
| `ChatPromptTemplate` | 变量对象 → 格式化消息 | 变量名、角色、顺序、转义 |
| `MessagesPlaceholder` | 消息数组 → 插入历史消息 | 它不是一段拼接后的聊天字符串 |
| ChatModel | 消息 → `AIMessage` | 实际请求与响应内容形状 |
| `StringOutputParser` | 消息 → 文本 | 它不保证 JSON、结构化字段或事实正确 |
| Runnable 管道 | 上一步输出 → 下一步输入 | `.pipe()` 不是任意函数都能随便拼 |
| LangSmith trace | 执行过程 → 外部观测记录 | 输入输出、层级、错误与隐私边界 |

你可以用 `请求 DTO → 中间转换 → SDK → 响应适配` 类比提示词管道。
历史消息保留 human / ai 等角色，比把聊天记录塞进一条 system 消息更清晰。
追踪用于解释一次执行发生了什么，不替代测试，也不自动给出质量结论。

## 6. 三个分级练习

### A · 基础：只验模板，不验“聪明程度”

- **输入**：在练习模板中使用变量 `question`，值为“用 Node 类比解释消息角色”；历史为 `[]`。
- **操作**：保留一条 system 指令、一个历史 placeholder 和一条当前 human 消息，先检查格式化结果。
- **预期行为**：当前问题出现在 human 消息中；空历史不产生虚构的历史消息。
- **证据**：记录消息数量、角色顺序以及变量替换位置，不要求固定假回复解释这个问题。
- **验收**：你能指出模板格式化结束的位置与模型调用开始的位置。

### B · 进阶：让输入错误显式出现

- **输入**：历史为 human“后续请给 TypeScript 示例”、ai“好的”；当前问题为“解释 stream”。
- **操作**：使用同一练习模板，再分别省略必需的 `question` 与必需的历史变量。
- **预期行为**：完整输入保留 system → human → ai → human 的顺序；缺少必需变量不能静默成功。
- **检查**：若你将 placeholder 配成可选项，说明空历史的默认行为，不把它误判成缺参漏洞。
- **证据**：保存正常的角色列表与缺参错误摘要，并标出错误发生在模型调用前。

### C · 挑战：做一份追踪准入清单

- **输入**：一条匿名问题、默认模式、`--trace` 单独出现、显式 `--live --trace` 三种设置。
- **操作**：默认模式实际运行；非法组合检查 runtime；真实追踪只在你自愿时执行。
- **预期行为**：默认不上传；单独 `--trace` 不获准联网；选中的 live + trace 才具备上传条件。
- **设计**：列出应删去的密钥、个人信息、内部 URL，以及可保留的匿名字段和错误类别。
- **证据**：把“实际观察”“源码依据”“未执行计划”分开写，不用计划冒充 trace 结果。

## 7. 证据清单与易踩坑

- [ ] 我记录了模板变量及各自的类型、来源和必需性。
- [ ] 我保存了最终消息角色列表，而不只是模型展示文本。
- [ ] 我验证了一条缺参路径，或明确写出可选 placeholder 的行为。
- [ ] 我标明追踪是否实际启用，未执行的线上检查单独列出。
- [ ] 我知道 trace 可能包含完整输入输出，提交前已做脱敏。

不要把 `MessagesPlaceholder` 的名字与业务变量名混用，否则历史可能被覆盖。
不可信文本即使放进 human 消息，也不自动消除提示注入风险；后续工具权限仍必须受控。
固定假响应不随模板语义变化，今天验证的是渲染与组合，不是提示词效果。
开了 trace 不代表你已经有告警、保留策略或访问控制；这些是另外的工程工作。

## 8. 五道自测（附简答）

1. **为什么先检查最终消息？** 模板变量、角色和历史顺序错误可以在付费调用前发现。
2. **placeholder 接收聊天记录字符串吗？** 本练习传消息数组，保留消息角色和顺序。
3. **parser 能保证合法结构化 JSON 吗？** 不能；文本提取与 schema 验证是不同职责。
4. **运行 `example:trace` 就会上传吗？** 不会；默认离线，追踪需要显式 live + trace 选择。
5. **trace 是模型质量评测吗？** 不是；它提供执行证据，质量评估还需要样本和标准。
