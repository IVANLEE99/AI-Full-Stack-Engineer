## 0. 先读结论

按 **mysql-pro** 优先级理解这四件事：

```text
1. 数据正确性     → 主库是真相源；从库/缓存都可能旧
2. 安全可恢复     → 备份要 PITR + 定期恢复演练
3. 证据驱动性能   → 先 EXPLAIN/慢日志，再读写分离，最后分片
4. 运维可维护     → 能不分片就不分片；能应用层解决就不上中间件
```

Day07 核心句：

> **没有验证过的备份等于没有备份；主从延迟让读副本不是实时真相；分库分表是最后手段。**

## 1. 备份与恢复

### 1.1 先定 RPO / RTO

| 指标 | 含义 | 工程问法 |
|------|------|----------|
| **RPO**（Recovery Point Objective） | 最多能接受丢多少数据 | 主库挂了，能回到几分钟前？ |
| **RTO**（Recovery Time Objective） | 最多能接受停多久 | 多久能恢复服务？ |

备份策略是为 RPO/RTO 服务的，不是「每天 dump 一下」就完事。

### 1.2 三种备份类型

| 类型 | 工具/手段 | 适合 | 局限 |
|------|-----------|------|------|
| **逻辑全量** | `mysqldump` | 小中库、迁移、lab | 大库慢、恢复慢 |
| **物理全量** | Percona XtraBackup、云 RDS 快照 | 大库热备 | 依赖版本/工具链 |
| **增量 / PITR** | **binlog** 连续归档 | 恢复到任意时间点 | 要有完整 binlog 链 |

**mysql-pro 铁律：**

```text
A backup is not proven until a restore has been tested.
备份没做过恢复演练 = 没备份
```

### 1.3 2026 推荐组合

```text
全量（日/周，视体量） + 连续 binlog + 异地一份 + runbook
```

| 环境 | 常见做法 |
|------|----------|
| **云 RDS / Aurora / 托管 MySQL** | 自动快照 + PITR；仍要跨账号/跨区复制 + **演练恢复** |
| **自建 K8s / VM** | XtraBackup + binlog 归档到对象存储（S3/OSS） |
| **本地 lab** | `mysqldump --single-transaction` 够练手 |

### 1.4 lab 最小演练

```bash
# 备份
mysqldump -u root -p --single-transaction --routines shop_lab > shop_lab_bak.sql

# 演练恢复到另一库名
mysql -u root -p -e "CREATE DATABASE shop_lab_restore DEFAULT CHARSET utf8mb4"
mysql -u root -p shop_lab_restore < shop_lab_bak.sql
```

演练后校验：**行数、checksum、抽几条业务 SQL**——不是「导入没报错」就算成功。

### 1.5 备份 checklist

| ✅ 要做 | ❌ 别做 |
|--------|--------|
| `--single-transaction`（InnoDB 一致性快照） | 生产高峰全库锁表 dump |
| 备份文件加密、权限隔离 | 备份含密码进 git |
| 保留周期满足合规 + RPO | 只留一份、和同机房同毁 |
| 写 **恢复 runbook** | 从没在 staging 恢复过 |

### 1.6 与变更的关系

大表 DDL、批量回填、分片迁移前：

```text
1. 确认备份/PITR 可用
2. 估 replication lag、磁盘、MDL
3. 有 forward-fix / rollback 方案
```

## 2. 主从复制与延迟

### 2.1 原理

```text
主库写 → 写 binlog
  → 从库 IO 线程拉 binlog
  → 从库 SQL 线程回放
  → 从库数据「追赶」主库

延迟 = 从库回放速度 < 主库写入速度（或回放被大单条拖住）
```

### 2.2 复制模式（2026 选型直觉）

| 模式 | 特点 | 何时考虑 |
|------|------|----------|
| **异步** | 性能最好；主挂可能丢未复制事务 | 读多写少、可接受最终一致 |
| **半同步** | 至少一个从库确认收到 binlog | 降低「主挂丢数据」风险 |
| **GTID** | 全局事务 ID，故障切换更简单 | MySQL 8 生产默认思路 |
| **组复制 / InnoDB Cluster** | 更高可用、选主 | 金融级；很多团队交给云托管 |

### 2.3 延迟从哪来？

| 原因 | 例子 |
|------|------|
| 从库硬件差 | 主 SSD、从 HDD |
| 大事务 / 批量写 | 一次 UPDATE 百万行 |
| DDL 在从库回放 | Online DDL 仍可能拉高 lag |
| 从库承担只读流量 | 读太重，回放抢 CPU/IO |
| 并行回放不足 | 单线程回放瓶颈 |

监控信号：

```text
Seconds_Behind_Master（传统）
performance_schema / 云监控 replication lag
应用层：写后读从库命中率 vs 投诉率
```

### 2.4 延迟的业务含义

```text
主库：order_id=10086 已 COMMIT
从库：lag 5 秒 → 这 5 秒内读从库看不到 10086
```

**从库不是「实时真相」**，只是 **延迟副本**。  
涉及 replication 的方案必须考虑 **read-after-write**。

## 3. 读写分离与一致性

### 3.1 架构

```text
写（INSERT/UPDATE/DELETE）→ 主库（Primary）
读（SELECT）            → 从库（Replica）降压
```

收益：分担读压力、水平扩展读能力。  
代价：**一致性复杂度**上升。

### 3.2 核心风险：写后读（Read-After-Write）

```text
用户下单成功（写主库）
  → 立刻打开「我的订单」（读从库）
  → 订单列表为空
```

这是读写分离的 **头号产品 bug**，不是 MySQL bug。

### 3.3 常见对策（按推荐度）

| 策略 | 做法 | 适用 |
|------|------|------|
| **写后关键读走主** | 下单/支付/改密后，下一跳强制 `readPrimary()` | 最稳、最常用 |
| **会话粘滞** | 同一用户写后 N 秒内读主 | 列表页、个人中心 |
| **延迟双读** | 读从库 miss → 再读主库 | 折中，多一次 RT |
| **同步复制 / 等从库** | 半同步 + 读已同步从库 | 成本高 |
| **产品接受最终一致** | 「订单处理中，请刷新」 | 非关键路径 |

**mysql-pro 原则：**

```text
读写分离是性能手段，不是强一致手段。
必须在 Service 层显式定义：哪些读可以旧、哪些读必须新。
```

### 3.4 应用层落点（Repository 路由）

```text
Controller → Service → Repository → MySQL
                         ↑
              这里决定走主还是走从
```

示例契约：

```php
// 写
$repo->createOrder($data);           // 写主库

// 写后立刻展示
$repo->findByOrderNo($no, primary: true);  // 强制主库

// 首页列表、统计报表
$repo->listByUserId($uid);           // 可走从库
```

路由逻辑集中在 Repository / 连接层，不要散落在 Controller。

### 3.5 与 Redis 的关系

```text
读：Redis 命中 → 返回
    未命中 → 读 MySQL（从库）→ 回填 Redis

写：先写 MySQL 主库成功 → 删/失效缓存
```

三层都可能旧：**从库 lag + 缓存 TTL**。  
**MySQL 主库是真相源**；TTL 只定义「可接受的旧窗口」。

## 4. 分库分表决策

### 4.1 决策树

```text
真有容量/吞吐问题吗？
  否 → 优化 SQL / 索引 / 缓存 / 硬件 / 只读副本
  是 → 单表过大或热点？
         → 归档冷数据、分区表、读写分离
         → 仍不够 → 再评估分片
```

**2026 最佳实践：分片是最后手段，不是架构炫技。**

很多团队 Day5 就能解决：

1. 错误 SQL / 缺索引  
2. 没缓存  
3. 没读副本  
4. 没归档历史订单  

就上 ShardingSphere —— **过度设计**。

### 4.2 什么时候「可以考虑」分片？

| 信号 | 说明 |
|------|------|
| 单表 **行数/体积** 持续超标 | 数亿行、TB 级且索引维护变慢 |
| **写 QPS** 单主顶不住 | 垂直扩容仍不够 |
| **热点行** 集中 | 有时 Redis 预扣优于分片 |
| 备份/DDL **窗口不可接受** | 大表变更动辄数小时 |

### 4.3 垂直拆 vs 水平拆

| 类型 | 含义 | 例子 | 复杂度 |
|------|------|------|--------|
| **垂直拆库** | 按业务拆不同库 | 用户库 + 订单库 | 中 |
| **水平分片** | 同构表按 key 分片 | `orders` 按 `user_id % 16` | **高** |

**优先垂直拆业务边界**，水平分片留给真正的大数据表。

### 4.4 分片键怎么选？

好分片键：

- **高基数**（值分散）  
- **查询大多带分片键**（避免全分片广播）  
- **增长均匀**（避免热点分片）

订单场景常见：`user_id`、`order_id`（雪花 ID）、`tenant_id`（多租户）。

**避免：** 按时间单分片（月底热点）、按 `status` 分片（全挤一片）。

### 4.5 分片后的痛点

| 痛点 | 后果 |
|------|------|
| 跨库 JOIN | 应用层组装或宽表/冗余 |
| 分布式事务 | 尽量 **避免**；Outbox / Saga / 最终一致 |
| 全局排序分页 | `ORDER BY created_at LIMIT 10` 要扫全分片 |
| 扩容 **re-shard** | 迁移成本极高 |
| 全局唯一 ID | 雪花、号段；UUID 无序伤 InnoDB |

中间件（ShardingSphere、Vitess）——**7 天会判断要不要用即可**。

### 4.6 先于分片的替代方案

| 方案 | 何时先用 |
|------|----------|
| **分区表** | 按时间归档，仍在单库 |
| **冷数据归档** | 历史订单迁冷库 |
| **只读副本** | 读扩展，不分片 |
| **缓存 + 异步** | 读多写少 |
| **云托管 DB** | Aurora 读副本、Serverless 弹性 |

## 5. 四者关系

```text
                    真相与恢复
                       │
              主库 Primary ←── 全量备份 + binlog PITR
                       │
              binlog 复制（有 lag）
                       │
              从库 Replica ←── 默认读流量
                       │
         写后关键读 ────┴──── 仍回主库

         单库仍不够 ──→ 水平分片（最后手段）
```

## 6. 2026 最佳实践速查

| 主题 | 做 | 不做 |
|------|----|------|
| **备份** | 全量+binlog、异地、加密、**季度恢复演练** | 从没恢复过就信备份 |
| **主从** | 监控 lag、大事务拆分、从库规格合理 | 以为从库=主库实时 |
| **读写分离** | 写后关键读走主；Repository 显式路由 | 全局读从、写后立刻列表 |
| **分片** | 先 SQL/索引/缓存/副本/归档 | 百万行就上中间件 |
| **变更** | expand/contract、估 lag、有回滚 | 大表 ALTER 不备份 |
| **安全** | 最小权限、参数绑定、脱敏导出 | 应用账号给 `DROP` |

## 7. 面试速答

| 题 | 答 |
|----|-----|
| 备份如何证明有效？ | 定期恢复到 staging，校验行数与业务 SQL |
| 主从延迟对用户的影响？ | 写后读从库可能看不到新数据 |
| 读写分离怎么保证一致？ | 写后关键读走主 / 会话粘滞 / 接受最终一致 |
| 什么时候不该分库分表？ | 没优化 SQL/索引/缓存/副本之前 |
| Repository 谁决定走主从？ | Repository 数据访问层；业务规则在 Service |
