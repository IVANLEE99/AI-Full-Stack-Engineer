## 1. 开始前的环境检查

动手前先确认工具链和已有资源，避免后面误判。

### 1.1 检查 Docker 是否就绪

```bash
docker --version
docker compose version
```

参数说明：这两个命令**没有参数**，只读版本号。

实测输出：

```text
Docker version 29.1.3, build f52814d
Docker Compose version v2.40.3-desktop.1
```

**判读要点**：Compose 是 `v2.x`，命令写作 `docker compose`（中间是空格）。如果你看到的是 `docker-compose`（带连字符），那是 v1 的老写法，本文所有命令都不适用。

### 1.2 检查已有容器和镜像

```bash
docker ps -a
docker images
```

| 命令 | 参数 | 含义 |
|---|---|---|
| `docker ps -a` | `-a` = `--all` | 列出**所有**容器，含已退出的；不加 `-a` 只看运行中的 |
| `docker images` | 无 | 列出本地镜像 |

**为什么要先查**：避免端口冲突、避免重复拉取镜像。

实测发现（开始前）：

```text
mm-redis    redis:7    Exited (0) 7 weeks ago
```

只有一个 7 周前退出的 `mm-redis`，没有 PHP 镜像。所以后面所有端口都刻意错开。

### 1.3 检查磁盘占用

```bash
docker system df
```

| 参数 | 含义 |
|---|---|
| 无 | `df` = disk free，显示镜像/容器/卷/构建缓存各占多少 |

实测：

```text
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          18        11        5.478GB   3.617GB (66%)
Containers      42        22        925.7kB   458.8kB (49%)
Local Volumes   2         1         89B       0B (0%)
Build Cache     84        0         3.182GB   2.371GB (66%)
```

**判读要点**：`RECLAIMABLE` 是可回收空间。后面要拉 PHP + MySQL + RabbitMQ 三个镜像，约需 1–2 GB，先确认够用。

## 2. 学习环境的设计

### 2.1 四个服务与端口规划

| 服务名 | 容器名 | 本机端口 → 容器端口 | 用途 |
|---|---|---|---|
| `php` | `learn-php` | 无（不对外） | 跑 PHP 代码 |
| `mysql` | `learn-mysql` | **3307** → 3306 | 避免和本机 3306 冲突 |
| `redis` | `learn-redis` | **6380** → 6379 | 避免和已有 redis 冲突 |
| `rabbitmq` | `learn-rabbitmq` | **5673** → 5672（AMQP）<br>**15673** → 15672（管理台） | 队列实验 |

**端口为什么错开**：

`-p 3307:3306` 的格式是 **`本机端口:容器端口`**。容器内的 MySQL 永远监听 3306，是你在 Mac 上访问时改用 3307。如果本机 3306 已被占用，直接用 3306 会报 `bind: address already in use`。

### 2.2 三个必须理解的配置概念

| 概念 | 在 compose 里叫什么 | 作用 | 类比 |
|---|---|---|---|
| **服务名** | `services:` 下的 key | 容器间互相访问用的主机名 | 局域网里的机器名 |
| **端口映射** | `ports:` | 本机能访问容器 | 路由器端口转发 |
| **目录挂载** | `volumes:` | 本机目录 ↔ 容器目录 | 共享文件夹 |

**服务名是最关键的**。compose 会创建一张内部网络，给每个服务登记 DNS，`redis` 这个名字会解析到 `learn-redis` 容器的 IP。容器内的 `127.0.0.1` 永远指**容器自己**。

## 3. 创建配置文件

### 3.1 Dockerfile

`php/week08/docker/Dockerfile`：

```dockerfile
# 学习用 PHP 环境：与 day04 六条标准一一对应
# 基础镜像固定版本 —— 这就是「容器 PHP ≠ 本机 PHP」的证据
FROM php:8.2-cli

# pdo_mysql 是 PHP 自带的，直接编译；sockets 是 php-amqplib 3.x 的硬依赖
RUN docker-php-ext-install pdo_mysql sockets

# redis / amqp 需要 pecl；amqp 依赖 librabbitmq-dev
RUN apt-get update \
    && apt-get install -y --no-install-recommends librabbitmq-dev libssl-dev unzip \
    && pecl install redis amqp \
    && docker-php-ext-enable redis amqp \
    && rm -rf /var/lib/apt/lists/*

# composer：从官方安装脚本装，避免多拉一个镜像
RUN curl -sS https://getcomposer.org/installer -o /tmp/composer-setup.php \
    && php /tmp/composer-setup.php --install-dir=/usr/local/bin --filename=composer \
    && rm /tmp/composer-setup.php

WORKDIR /app

CMD ["tail", "-f", "/dev/null"]
```

逐行说明：

| 行 | 作用 | 为什么这么写 |
|---|---|---|
| `FROM php:8.2-cli` | 基础镜像 | 固定小版本前两位，保证可复现 |
| `docker-php-ext-install pdo_mysql sockets` | 编译内置扩展 | 这两个是 PHP 源码自带的 |
| `apt-get install librabbitmq-dev` | 装 C 库 | `amqp` 扩展编译时需要它 |
| `pecl install redis amqp` | 装第三方扩展 | PECL 是 PHP 扩展仓库 |
| `docker-php-ext-enable` | 生成 ini 启用扩展 | 光装上不启用不生效 |
| `rm -rf /var/lib/apt/lists/*` | 清 apt 缓存 | 减小镜像体积 |
| `curl getcomposer.org/installer` | 装 composer | 避免额外拉 `composer:2` 镜像 |
| `CMD ["tail","-f","/dev/null"]` | 让容器常驻 | CLI 镜像默认没有前台进程，会立刻退出 |

**关于 `sockets`**：这是踩坑后补的。`php-amqplib` 3.x 声明了 `ext-sockets` 硬依赖，不装就 `composer require` 失败。

### 3.2 docker-compose.yml

`php/week08/docker/docker-compose.yml`：

```yaml
name: learn-env

services:
  php:
    build: .
    container_name: learn-php
    volumes:
      - ..:/app
    environment:
      DB_HOST: mysql
      DB_PORT: 3306
      REDIS_HOST: redis
      REDIS_PORT: 6379
      RABBITMQ_HOST: rabbitmq
      RABBITMQ_PORT: 5672
    depends_on:
      - mysql
      - redis
      - rabbitmq
    networks:
      - learn

  mysql:
    image: mysql:8.0
    container_name: learn-mysql
    ports:
      - "3307:3306"
    environment:
      MYSQL_ROOT_PASSWORD: root123
      MYSQL_DATABASE: learn
    volumes:
      - mysql-data:/var/lib/mysql
    networks:
      - learn

  redis:
    image: redis:7-alpine
    container_name: learn-redis
    ports:
      - "6380:6379"
    networks:
      - learn

  rabbitmq:
    image: rabbitmq:3-management
    container_name: learn-rabbitmq
    ports:
      - "5673:5672"
      - "15673:15672"
    environment:
      RABBITMQ_DEFAULT_USER: admin
      RABBITMQ_DEFAULT_PASS: admin123
    networks:
      - learn

volumes:
  mysql-data:

networks:
  learn:
    driver: bridge
```

逐项说明：

| 字段 | 值 | 含义 |
|---|---|---|
| `name: learn-env` | 项目名 | 决定容器名前缀、网络名、卷名。不写则用**目录名**（会变成 `docker`，极易撞名） |
| `build: .` | 构建上下文 | 用当前目录的 Dockerfile 构建，而不是拉现成镜像 |
| `container_name` | 固定名字 | 方便 `docker exec learn-php`，不写则自动生成随机名 |
| `volumes: - ..:/app` | 相对路径挂载 | `..` 是 `php/week08/`，挂到容器 `/app`。`:` 左本机、右容器 |
| `volumes: mysql-data:/var/lib/mysql` | 命名卷 | MySQL 数据持久化，`docker compose down` 不删 |
| `ports: "3307:3306"` | 字符串 | **必须加引号**，否则 YAML 可能解析成六十进制数字 |
| `environment` | 环境变量 | 这里的 `mysql` 是服务名，不是地址 |
| `depends_on` | 启动顺序 | 只保证**启动顺序**，不保证服务**就绪**（后面要用 ping 等待） |
| `networks` | 自定义网络 | 四个服务在同一网络内才能用服务名互访 |

**`depends_on` 的坑**：它只保证 `mysql` 容器先**启动**，不保证 MySQL **可以接受连接**。MySQL 初始化要十几秒，所以后面必须主动 `ping` 等待。

### 3.3 校验配置语法

```bash
docker compose config --quiet
docker compose config
```

| 命令 | 参数 | 作用 |
|---|---|---|
| `docker compose config` | 无 | 把 YAML 解析成规范化的完整配置并打印，**能发现语法错误** |
| 同上 | `--quiet` / `-q` | 只校验不输出，成功无回显 |

**为什么先校验**：`up` 失败时报错信息可能很模糊，先 `config` 能提前暴露 YAML 缩进、引号、字段名等问题。

实测：`COMPOSE OK`（静默通过）。

## 4. 六条标准逐条完成

### 标准 1：能启动 Docker 环境 ✅

#### 命令

```bash
cd php/week08/docker
docker compose up -d
docker compose ps
```

#### 参数说明

| 命令/参数 | 全称 | 含义 |
|---|---|---|
| `up` | — | 创建并启动 `services:` 下所有服务 |
| `-d` | `--detach` | 后台运行，不占用终端。不加会占住终端并打印所有日志 |
| `ps` | — | 列出本项目的容器状态（等价于 `docker ps` 但只看本项目） |

#### 实测输出

```text
Network learn-env_learn  Creating
Volume learn-env_mysql-data  Creating
Container learn-rabbitmq  Creating
Container learn-redis  Creating
Container learn-mysql  Creating
Container learn-php  Creating
Container learn-mysql  Starting
...
```

最终状态：

```text
NAME             IMAGE                   STATUS          PORTS
learn-mysql      mysql:8.0               Up 27 minutes   0.0.0.0:3307->3306/tcp, [::]:3307->3306/tcp
learn-php        learn-env-php           Up 8 minutes
learn-rabbitmq   rabbitmq:3-management   Up 27 minutes   0.0.0.0:5673->5672/tcp, 0.0.0.0:15673->15672/tcp
learn-redis      redis:7-alpine          Up 27 minutes   0.0.0.0:6380->6379/tcp
```

#### 判读

- `Up` 就是运行中；出现 `Restarting` 说明启动即崩，要 `docker compose logs <服务名>` 查原因。
- `PORTS` 列 `0.0.0.0:3307->3306/tcp` 读法：左 `3307` 是本机端口，右 `3306` 是容器端口。
- `learn-php` 没有 PORTS，因为它不需要从本机直接访问——我们通过 `docker compose exec` 进去。

#### 额外：确认 MySQL 真的能服务

`Up` 不等于 `可用`。MySQL 首次启动要初始化数据目录，约 10–30 秒。

```bash
docker exec learn-mysql mysqladmin ping -uroot -proot123
```

| 参数 | 含义 |
|---|---|
| `docker exec` | 在**运行中**的容器里执行命令 |
| `learn-mysql` | 目标容器名 |
| `mysqladmin ping` | MySQL 自带健康检查命令 |
| `-uroot` | `-u` = user，用户 root（`-u` 和值之间**不能有空格**） |
| `-proot123` | `-p` = password（同样不能有空格） |

实测输出：

```text
mysqladmin: [Warning] Using a password on the command line interface can be insecure.
mysqld is alive
```

**判读**：`mysqld is alive` 才是真的可用了。那句 `Warning` 是提醒你命令行传密码不安全，学习环境可忽略，生产应改用 `~/.my.cnf`。

如果立刻执行会看到：

```text
mysqld: Can't connect to local MySQL server through socket ...
```

这就是**没等够**，不是配置错。

### 标准 2：能进入 PHP 容器 ✅

#### 命令

```bash
docker compose exec php bash
```

#### 参数说明

| 参数 | 含义 |
|---|---|
| `exec` | 在**已运行**的容器里执行命令（不是新起容器） |
| `php` | compose 里的**服务名**（也可以用容器名 `learn-php`） |
| `bash` | 在容器内启动 bash，进入交互式 shell |

#### 与 `docker run` 的区别（重要）

| | `docker exec` | `docker run` |
|---|---|---|
| 对象 | 已在运行的容器 | 用镜像**新建**容器 |
| 状态 | 进入现有环境，改动保留 | 每次都是全新实例 |
| 用途 | 进容器排查、执行命令 | 启动新服务 |

#### 实测输出

```text
当前目录: /app
主机名(容器ID): 9d84b69ddfc0
挂载进来的文件数: 15
```

#### 判读

- `pwd` 是 `/app` —— 由 Dockerfile 的 `WORKDIR /app` 决定
- `ls` 能看到 `day01.md`、`RabbitMq.php` —— 因为 compose 写了 `volumes: - ..:/app`
- 文件数是 **15**，这是 `php/week08/` 当前的文件/目录数

#### 验证挂载是双向的

在容器里建文件，本机立刻能看到：

```bash
docker compose exec php bash -c 'echo hello > /app/docker/mount-test.txt'
cat php/week08/docker/mount-test.txt
# hello
```

**这说明**：volume 是**同一个目录的两条路径**，不是复制。所以改代码不用重建镜像。

反过来也一样：你在 IDE 里改 `RabbitMq.php`，容器里立刻就是新内容。

### 标准 3：能查看 PHP 版本和扩展 ✅

#### 命令

```bash
docker compose exec php php -v
docker compose exec php php -m
```

#### 参数说明

| 参数 | 含义 |
|---|---|
| `php -v` | `-v` = version，打印 PHP 版本和编译信息 |
| `php -m` | `-m` = modules，列出**所有已启用的扩展** |

#### 实测输出：版本对比

```bash
echo "=== 容器 ==="; docker compose exec php php -v | head -2
echo "=== 本机 ===";   php -v | head -2
```

```text
=== 容器 ===
PHP 8.2.35 (cli) (built: Oct 28 2026 01:30:40) (NTS)

=== 本机 ===
PHP 8.5.8 (cli) (built: Jul  1 2026 03:46:27) (NTS)
```

#### 实测输出：扩展对比

```bash
echo "=== 容器 ==="; docker compose exec php php -m | grep -E '^(redis|amqp|sockets|pdo_mysql)$'
echo "=== 本机 ===";   php -m | grep -E '^(redis|amqp|sockets|pdo_mysql)$'
```

```text
=== 容器 ===
amqp
pdo_mysql
redis
sockets

=== 本机 ===
pdo_mysql
sockets
```

#### 判读 —— 这是全篇最重要的证据

| | 版本 | redis | amqp | pdo_mysql | sockets |
|---|---|---|---|---|---|
| 容器 `learn-php` | **8.2.35** | ✅ | ✅ | ✅ | ✅ |
| 本机 Homebrew | **8.5.8** | ❌ | ❌ | ✅ | ✅ |

两个结论：

1. **版本不同**：8.2 vs 8.5，跨三个小版本。
2. **扩展不同**：本机**缺 `redis` 和 `amqp`**。这意味着本周写的缓存与 MQ 代码，**在本机根本跑不起来**。

所以排查"代码跑不通"时，第一步不是看代码，是确认你在哪跑。

#### 常用扩展检查片段

```bash
# 只看关键扩展是否存在
docker compose exec php php -r 'foreach(["redis","amqp","pdo_mysql","sockets"] as $e){ echo $e.": ".(extension_loaded($e)?"YES":"NO")."\n"; }'
```

| 片段 | 含义 |
|---|---|
| `extension_loaded($e)` | PHP 函数，判断扩展加载与否 |
| 用 `php -r` 而非 `php -m` | 适合写进脚本做断言 |

### 标准 4：能查看至少 2 类日志 ✅

日志有两个**完全不同**的来源，都要会看。

#### 第一类：服务自身日志

```bash
docker compose logs --tail=5 redis
docker compose logs --tail=8 rabbitmq
```

| 参数 | 全称 | 含义 |
|---|---|---|
| `logs` | — | 打印服务标准输出/错误 |
| `--tail=N` | — | 只看**最后 N 行**；不写会打印全部历史 |
| `-f` | `--follow` | 持续跟踪，类似 `tail -f`，`Ctrl+C` 退出 |
| `--since=10m` | — | 只看最近 10 分钟（也支持 `2026-11-03T10:00:00`） |
| `--timestamps` / `-t` | — | 每行前加时间戳 |

**实测输出（Redis）**：

```text
learn-redis  | 1:M 03 Nov 2026 07:29:59.197 * Running mode=standalone, port=6379.
learn-redis  | 1:M 03 Nov 2026 07:29:59.198 * Server initialized
learn-redis  | 1:M 03 Nov 2026 07:29:59.201 * Ready to accept connections tcp
```

**实测输出（RabbitMQ）**：

```text
learn-rabbitmq  | [info] <0.692.0> Server startup complete; 5 plugins started.
learn-rabbitmq  | [info] <0.692.0>  * rabbitmq_management
learn-rabbitmq  | [info] <0.9.0> Time to start RabbitMQ: 8588 ms
```

判读：`Ready to accept connections` / `Server startup complete` 才是**真正可接客**的标志，比 `Up` 更准。

**RabbitMQ 还能看到连接日志**，这条对排查 MQ 问题极有用：

```text
learn-rabbitmq | connection <0.1199.0> (172.18.0.5:52334 -> 172.18.0.3:5672):
                 user 'admin' authenticated and granted access to vhost '/'
```

读法：`172.18.0.5` 是 PHP 容器，`172.18.0.3` 是 RabbitMQ 容器——**证明流量确实走了内部网络，而且用的是服务名解析出的 IP**。

#### 第二类：应用日志（容器写、本机读）

```bash
# 容器内写
docker compose exec php bash -c 'echo "[$(date "+%F %T")] INFO test" >> /app/docker/logs/app.log'

# 本机读同一个文件
cat php/week08/docker/logs/app.log
```

**实测输出**：

```text
[2026-11-03 15:35:51] INFO 容器内写入的日志
```

#### 判读 —— 两类日志怎么选

| 类型 | 命令 | 适合看什么 | 数据在哪 |
|---|---|---|---|
| 服务日志 | `docker compose logs` | 进程启动、崩溃、连接失败 | Docker 引擎 |
| 应用日志 | 直接读文件 | 业务异常、请求追踪、慢查询 | volume 挂载目录 |

**根本区别**：服务日志由 Docker 收集，容器删除就没了；应用日志写在挂载目录，**容器删了文件还在**。

### 标准 5：能说明容器和本地 PHP 的差异 ✅

这条不敲命令，考的是能不能讲清楚。用实测数据回答：

#### 五项实测差异

| 对比项 | 本机 | 容器 | 实际后果 |
|---|---|---|---|
| **版本** | 8.5.8 | 8.2.35 | 新语法本机能跑、容器可能报错；反之弃用告警不同 |
| **redis 扩展** | ❌ | ✅ | 本机跑缓存代码直接 `Class "Redis" not found` |
| **amqp 扩展** | ❌ | ✅ | 本机跑本周 MQ 代码直接失败 |
| **`localhost`** | 指 Mac 自己 | 指容器自己 | 连接串写 `127.0.0.1` 必然连不上 |
| **路径** | `/Users/...` | `/app` | 配置里的绝对路径全部失效 |
| **php.ini** | Homebrew 的 | 镜像的 | 内存限制、时区、上传大小可能不同 |

#### 一句话总结

> **代码跑在容器里，就用容器里的 PHP 判断问题。**
> 本机 `php -v` 只能说明你的 CLI 环境，**不能说明服务运行环境**。

#### 怎么快速自查

```bash
# 本机
php -v; php -m | grep -E 'redis|amqp'

# 容器
docker compose exec php php -v
docker compose exec php php -m | grep -E 'redis|amqp'
```

两条命令的差异就是答案。

### 标准 6：能解释容器内为什么用服务名访问 ✅

#### 错误示范：用 `127.0.0.1`

```bash
docker compose exec php php -r '$r=new Redis(); $r->connect("127.0.0.1",6379,1); echo "成功";'
```

实测输出：

```text
失败: Connection refused
```

#### 正确做法：用服务名

```bash
docker compose exec php php -r '$r=new Redis(); $r->connect("redis",6379,2); echo "OK ping=".$r->ping();'
```

实测输出：

```text
OK ping=1
```

**同一个容器、同一个 PHP、同一个端口**，唯一区别就是主机名。

#### 为什么

```text
容器内的 127.0.0.1
  = learn-php 容器自己
  = 这台"机器"上并没有跑 Redis
  → Connection refused

容器内的 redis
  = compose 内部 DNS 解析
  = learn-redis 容器的 IP (172.18.0.2)
  → 连接成功
```

#### 验证 DNS 解析

```bash
docker compose exec php getent hosts redis mysql rabbitmq
docker compose exec php hostname -i
```

| 命令 | 参数 | 含义 |
|---|---|---|
| `getent hosts` | `hosts` | 用系统 NSS 查主机名 → IP，和程序内部解析走同一套逻辑 |
| `hostname -i` | `-i` = ip | 打印本机（此处是容器）IP |

实测输出：

```text
172.18.0.2      redis
172.18.0.4      mysql
172.18.0.3      rabbitmq

self=172.18.0.5
```

**关键观察**：四个 IP 各不相同。PHP 容器是 `.5`，它要访问的三个服务都在别的 IP 上——所以 `127.0.0.1` 永远指错地方。

#### 三个服务一次性连通

```bash
docker compose exec php php -r '
$r=new Redis(); $r->connect("redis",6379,2); echo "Redis: ".$r->ping()."\n";
$pdo=new PDO("mysql:host=mysql;port=3306;dbname=learn","root","root123"); echo "MySQL: ".$pdo->query("SELECT VERSION()")->fetchColumn()."\n";
$c=new AMQPConnection(); $c->setHost("rabbitmq"); $c->setPort(5672);
$c->setLogin("admin"); $c->setPassword("admin123"); $c->connect();
echo "RabbitMQ: ".($c->isConnected()?"连接成功":"失败")."\n";'
```

实测输出：

```text
Redis: 1
MySQL: 8.0.46
RabbitMQ: 连接成功
```

#### 本机访问时反过来

在 **Mac 上**（不是容器里），就要用 `127.0.0.1` + 映射端口：

| 从哪访问 | Redis 地址 | MySQL 地址 | RabbitMQ 管理台 |
|---|---|---|---|
| 容器内 | `redis:6379` | `mysql:3306` | `rabbitmq:15672` |
| Mac 本机 | `127.0.0.1:6380` | `127.0.0.1:3307` | `http://localhost:15673` |

**记忆法**：容器内用**服务名 + 容器端口**；本机用 **127.0.0.1 + 映射端口**。

## 6. 额外：真的跑通一次 MQ 收发

六条标准不要求，但这一步把 [day01](./day01.md) 的抽象概念变成可见输出。

### 6.1 装 php-amqplib

```bash
docker compose exec php composer require php-amqplib/php-amqplib:^3.7
```

| 参数 | 含义 |
|---|---|
| `composer require` | 添加依赖并写入 `composer.json` |
| `包名:^3.7` | `^` 表示"兼容 3.7 及以上的 3.x"，允许 3.8、3.9，不允许 4.0 |
| 执行位置 | 在 `/app` 下执行，所以文件落在 `php/week08/composer.json` |

实测装到 **v3.7.5**。

### 6.2 一个必须先搞清的坑

`RabbitMq.php` 用的 `PhpAmqpLib\Connection\AMQPStreamConnection` 是 **composer 库**的类；而 Dockerfile 里装的 `amqp` 是 **PHP 扩展**，提供的是另一套 API。

| | 来源 | 类名 | 怎么装 |
|---|---|---|---|
| `amqp` 扩展 | PECL | `AMQPConnection` | `pecl install amqp` |
| php-amqplib | composer | `PhpAmqpLib\Connection\AMQPStreamConnection` | `composer require` |

**两者不通用**。本周读的 `RabbitMq.php` 用的是**后者**。

- 验证扩展：`php -m | grep amqp`
- 验证库：`composer show php-amqplib/php-amqplib`

### 6.3 收发脚本

`php/week08/docker/demo_mq.php` 的关键代码：

```php
$exchange = 'payment.events';   // 交换机：决定怎么路由
$queue    = 'order_paid_queue'; // 队列：存消息
$routeKey = 'payment.succeeded'; // 路由键：消息类型

$conn = new AMQPStreamConnection('rabbitmq', 5672, 'admin', 'admin123');
$ch   = $conn->channel();

$ch->exchange_declare($exchange, 'direct', false, true, false);
[$queueName] = $ch->queue_declare($queue, false, true, false, false);
$ch->queue_bind($queueName, $exchange, $routeKey);

$msg = new AMQPMessage($payload, ['delivery_mode' => AMQPMessage::DELIVERY_MODE_PERSISTENT]);
$ch->basic_publish($msg, $exchange, $routeKey);
```

参数说明（与 `RabbitMq.php` 对应）：

| 参数 | 值 | 含义 |
|---|---|---|
| `AMQPStreamConnection` 第 1 个 | `rabbitmq` | 主机名，**用服务名** |
| 第 2 个 | `5672` | AMQP 端口（容器内端口，不是 5673） |
| `exchange_declare($name, $type, ...)` | `direct` | 交换机类型：按 route_key 精确匹配 |
| `queue_declare($name, ...)` | — | 声明队列，返回 `[队列名, 消息数, 消费者数]` |
| `queue_bind($queue, $exchange, $routeKey)` | — | 建立绑定关系 |
| `delivery_mode: PERSISTENT` | 2 | 消息持久化，Broker 重启不丢 |

```bash

```

### 8.3 `Class "AMQPStreamConnection" not found`

**原因**：把 **PHP 扩展** 当成了 **composer 库**。`amqp` 扩展提供的是 `AMQPConnection`，不是 `AMQPStreamConnection`。

**处理**：

```bash
docker compose exec php composer require php-amqplib/php-amqplib:^3.7
```

### 8.4 装成 v2.0.2 而不是 3.x

```text
- Installing php-amqplib/php-amqplib (v2.0.2)
```

**原因**：不指定版本时 composer 选了最低可用版本。

**处理**：显式指定约束：

```bash
docker compose exec php composer require php-amqplib/php-amqplib:^3.7
```

### 8.5 `docker compose` 报项目名冲突

**原因**：没写 `name:`，compose 用**目录名**做项目名。本目录叫 `docker`，项目名就成了 `docker`，容易和其他项目撞。

**处理**：compose 文件顶部显式声明：

```yaml

```

### 8.6 MySQL 刚 `Up` 就连不上

**原因**：`depends_on` 只保证启动顺序，不保证服务就绪。MySQL 初始化数据目录需要 10–30 秒。

**处理**：用 `mysqladmin ping` 轮询等待，或改用 `healthcheck` + `condition: service_healthy`。

### 8.7 浏览器打不开管理台：`HTTP ERROR 431` ⭐

**现象**：浏览器访问 <http://localhost:15673> 显示

```text
This page isn't working
HTTP ERROR 431
```

但容器明明 `Up`，端口也映射了。

#### 第一步：先别怀疑 Docker，用 curl 判断服务端

```bash
curl -s -o /dev/null -w "HTTP状态: %{http_code}\n" http://localhost:15673/
```

实测输出：

```text
HTTP状态: 200
```

再看响应头：

```bash
curl -sI http://localhost:15673/ | head -8
```

```text
HTTP/1.1 200 OK
content-type: text/html
server: Cowboy
```

**判读**：`200` + `server: Cowboy`（RabbitMQ 的 HTTP 服务器）说明**服务端完全正常**。问题在浏览器发出去的请求。

#### 第二步：确认服务端健康

```bash
docker exec learn-rabbitmq rabbitmq-diagnostics -q check_running
docker exec learn-rabbitmq rabbitmq-diagnostics -q version
docker exec learn-rabbitmq rabbitmq-plugins list -e | grep management
```

实测输出：

```text
RabbitMQ on node rabbit@b445ff5da734 is fully booted and running
3.13.7
[E*] rabbitmq_management       3.13.7
[e*] rabbitmq_management_agent 3.13.7
```

| 参数 | 含义 |
|---|---|
| `rabbitmq-diagnostics -q check_running` | `-q` = quiet，只输出结论；检查节点是否完全启动 |
| `rabbitmq-diagnostics -q version` | 打印版本 |
| `rabbitmq-plugins list -e` | `-e` = enabled，只列**已启用**的插件；`[E*]` 表示已启用 |

#### 第三步：复现 431，证明是 Cookie 太大

```bash
BIG=$(python3 -c "print('x'*9000)")
curl -s -o /dev/null -w "%{http_code}\n" -H "Cookie: big=$BIG" http://localhost:15673/
```

实测输出：

```text
431
```

对照：正常浏览器头 → `200`，带 9 KB Cookie → `431`。**原因确定**。

#### 原因

**HTTP 431 = `Request Header Fields Too Large`**，是请求头总量超限，不是连接失败、也不是 404。

RabbitMQ 的 Cowboy HTTP 服务器对请求头有上限（默认约 8 KB）。而浏览器**访问任何 `localhost` 端口时，会把该 host 下的所有 Cookie 一起发出去**。

你在本机开发时会访问大量 `localhost` 服务（本地项目、调试面板、各种前端 dev server），它们都在 `localhost` 这个 host 下种 Cookie。累积到超过 8 KB，RabbitMQ 在解析阶段就直接回 431，连登录页都来不及渲染。

> 这也解释了为什么「前几天还能打开，今天不行」——是 Cookie 累积的结果，不是环境坏了。

#### 处理（按推荐顺序）

**方案 1：无痕窗口（最快，用来验证诊断）**

| 浏览器 | 快捷键 |
|---|---|
| Chrome / Edge | `⌘ + Shift + N` |
| Safari / Firefox | `⌘ + Shift + P` |

无痕窗口不携带已有 Cookie，能打开就确诊无误。

**方案 2：换主机名 `127.0.0.1`（不用清数据）**

```text
http://127.0.0.1:15673
```

**原理**：Cookie 按 **host** 隔离，`127.0.0.1` 与 `localhost` 是两个不同 host，不共享 Cookie。

⚠️ **换端口无效**：`localhost:8080` 与 `localhost:15673` 共享同一批 Cookie，改成 `15674` 一样 431。起作用的是**主机名**，不是端口。

**方案 3：清掉 localhost 的 Cookie（彻底）**

| 浏览器 | 路径 |
|---|---|
| Chrome / Edge | 地址栏输入 `chrome://settings/content/all`，搜 `localhost`，删除 |
| Safari | `⌘ + ,` → 隐私 → 管理网站数据 → 搜 `localhost` → 移除 |
| Firefox | `⌘ + ,` → 隐私与安全 → Cookie 和网站数据 → 管理数据 → 搜 `localhost` → 移除 |

**方案 4：调大 RabbitMQ 的头上限（不推荐，仅了解）**

RabbitMQ 管理插件支持 `management.cowboy.max_header_value_length` 等配置。但这是治标——8 KB 已经很大，说明浏览器里堆了不该有的垃圾，清掉更干净。

#### 一句话总结

> **HTTP 431 不是连不上，是请求头太大。**
> 先 `curl` 确认服务端 `200`，再用无痕窗口或 `127.0.0.1` 绕过，最后清 `localhost` Cookie 根治。

#### 同类问题会出现在哪些地方

任何在 `localhost` 上跑、且对请求头大小敏感的 HTTP 服务都可能中招：

| 服务 | 默认端口 | 是否容易触发 |
|---|---|---|
| RabbitMQ 管理台 | 15672 | 是，Cowboy 限制较紧 |
| Nginx | 80 / 8080 | 是，`large_client_header_buffers` 控制 |
| Tomcat | 8080 | 是，`maxHttpHeaderSize` 默认 8 KB |
| Node/Express | 3000 等 | 是，Node 默认 `maxHeaderSize` 16 KB |
| Redis | 6379 | 否，不是 HTTP |

排查思路完全一样：**先 curl 看状态码，再判断是客户端还是服务端**。
